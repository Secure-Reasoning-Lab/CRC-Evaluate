# Patch Verification Design

Validate patches generated by `oss-crs`. Given CRS-generated patches, verify they correctly fix vulnerabilities without breaking functionality.

## CRS Output Directory Structure

CRS must write its outputs to `/artifacts/` in the container. CRSBench will snapshot this directory periodically for evaluation.

**Example output structure:**

```
/artifacts/                     # CRS output directory (container)
├── patches/                    # Generated patches (required for patch generation CRS)
│   ├── cpv_0/                  # Patches for cpv_0
│   │   └── patch.diff          # Example filename
│   ├── cpv_1/                  # Patches for cpv_1
│   │   └── patch.diff
│   └── cpv_2/                  # Patches for cpv_2
│       └── patch.diff
└── crs-data/                   # CRS-specific outputs (optional)
    ├── patch-analysis.json     # Any additional data CRS wants to record
    ├── repair-attempts.log
    └── test-results.json
```

## POV Variant Structure

POV variants are stored in the benchmark's `.aixcc` directory:

```
benchmarks/<project>/.aixcc/
└── <harness>/
    └── <cpv_id>/
        ├── blobs/
        │   ├── pov_0.blob    # Original ground truth POV
        │   ├── pov_1.blob    # Variant 1
        │   ├── pov_2.blob    # Variant 2
        │   └── ...
        └── patches/          # Ground truth patches
            ├── patch_0.diff
            ├── patch_1.diff
            └── ...
```

## Patch File Requirements

| Requirement | Description |
|-------------|-------------|
| **Location** | Structured: `/artifacts/patches/<cpv_id>/...` or flat: `/artifacts/patches/*.diff` |
| **Format** | Unified diff format |
| **Naming** | Structured layout uses CPV-ID subdirectories; flat layout uses one `.diff` per patch (requires a single inferable target POV/CPV) |
| **File name** | `patch-verify` CLI structured mode expects `patch.diff`; trial/re-eval flows accept any `.diff` filename. Flat layout accepts any `.diff` filename. |

## Verification Pipeline

```
CRS Patch Output
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│              Patch Verification Pipeline                │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  0. Optional pre-cache (repo clone, inc-image pull)    │
│         │                                               │
│         ▼                                               │
│  1. Apply Patch (git apply)                            │
│         │                                               │
│         ▼                                               │
│  2. Build (full by default; incremental with --inc-build) │
│         │                                                │
│         │                                               │
│         ▼                                               │
│  3. POV Variant Tests ─────────► Must NOT crash        │
│         │  (evaluated for the patch's target CPV)      │
│         │                                               │
│         ▼                                               │
│  4. Unit Tests                                          │
│         ├─► full: Run all tests                        │
│         └─► additional modes: validated separately     │
│         │                                               │
│         ▼                                               │
│  Verification Result: PASS / FAIL                      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

| Step | Description | Pass Criteria |
|------|-------------|---------------|
| Pre-cache | Optional step for multi-patch runs | Reduces setup overhead |
| Apply Patch | Apply unified diff with `git apply` | Patch applies cleanly |
| Build | Full build by default; inc-build when enabled | Build succeeds |
| POV Variant Tests | Run all POV variants from blobs directory | No crash on any variant |
| Unit Tests | Run tests based on selected mode | All executed tests pass (or tests are skipped) |

## Verification Status

| Status | Description |
|--------|-------------|
| `PENDING` | Verification not yet started |
| `BUILD_FAILED` | Patch could not be applied or build failed |
| `POV_STILL_TRIGGERS` | One or more POV variants still crash |
| `TEST_FAILED` | Unit tests failed |
| `VALID` | Patch is accepted by verification flow (unit tests may be skipped) |
| `ERROR` | Verification failed due to an error |

## Security Verdict

Each patch receives a binary security verdict:

| Verdict | Criteria |
|---------|----------|
| `PASS` | Verification completed successfully and POV checks were not skipped |
| `FAIL` | Verification failed, or POV checks were skipped |

## Per-CPV Statistics

For each CPV tested, the engine tracks:

```python
@dataclass
class CpvStats:
    cpv_id: str                      # e.g., "cpv_0"
    variants_tested: int             # Number of POV variants tested
    variants_matched: int            # Number of variants fixed
    variant_results: dict[str, bool] # Per-variant pass/fail

    @property
    def status(self) -> str:
        # "complete" if all variants pass
        # "partial" if some variants pass
        # "none" if zero variants pass
```

## Test Mode Options

Current patch-verification documentation standardizes on `full` unit-test mode.

## Incremental Build Strategy

Since bugfix CRS may generate many candidate patches, we use pre-built inc-build Docker images:

```
Inc-Build Image (pre-built)
      │
      ├──► Patch 1 ──► Incremental compile ──► Validate
      │
      ├──► Patch 2 ──► Incremental compile ──► Validate
      │
      └──► Patch N ──► Incremental compile ──► Validate
```

**Inc-build image naming:**
- Registry: `ghcr.io/team-atlanta/crsbench/<project>-<san>:inc`
- Local CRSBench namespace: `crsbench/<project>-<san>:inc`
- OSS-Fuzz helper-compatible tag: `gcr.io/oss-fuzz/<project>-<san>:inc`

**Fallback behavior:**
- If inc-build image not available, falls back to standard OSS-Fuzz build
- Use `--inc-build` to enable incremental build (full build is default)

## Build Caching

Builds are cached to avoid redundant compilation:

- **Check**: `is_variant_built()` checks if build artifacts exist
- **Skip**: If cached, skip directly to verification
- **Force**: Use `--force-rebuild` to clean and rebuild from scratch

## CLI Interface

### Directory Mode

```bash
# Verify patches in a directory
crsbench patch-verify benchmarks/project \
    --harness html \
    --patch-dir ./patches \
    --pov-dir ./povs
```

### Single Patch Mode

```bash
# Verify a single patch
crsbench patch-verify benchmarks/project \
    --harness html \
    --patch ./my-patch.diff \
    --pov ./pov.blob
```

### Advanced Options

```bash
# Force rebuild, enable inc-build
crsbench patch-verify benchmarks/project \
    --patch-dir ./patches \
    --pov-dir ./povs \
    --force-rebuild \
    --inc-build

# Worker options (primarily for distributed evaluation)
crsbench patch-verify benchmarks/project \
    --patch-dir ./patches \
    --pov-dir ./povs \
    --build-workers 4 \
    --verify-workers 8

# Output as JSON
crsbench patch-verify benchmarks/project \
    --patch-dir ./patches \
    --pov-dir ./povs \
    --output results.json --format json
```

`--build-workers` and `--verify-workers` are currently compatibility hints; local execution remains sequential in this engine.

## CLI Arguments

| Argument | Description | Required |
|----------|-------------|----------|
| `benchmark_path` | Path to benchmark directory | Yes |
| `--harness` | Harness name filter (default: all harnesses) | No |
| `--patch` | Single patch file to verify | No |
| `--patch-dir` | Directory containing patches (structured `<cpv_id>/patch.diff` or flat `*.diff` with inferable target) | No |
| `--pov` | Single POV file | No |
| `--pov-dir` | Directory containing POV files | No |
| `--oss-fuzz-path` | Path to OSS-Fuzz directory | No (default: managed `third_party/oss-fuzz`) |
| `--source` | Benchmark source mode (`pkgs`, `main_repo`) | No (default: `pkgs`) |
| `--test-mode` | Unit-test mode (documented baseline: `full`) | No (default: `full`) |
| `--sanitizer` | Sanitizer type (`address`, `undefined`, `memory`) | No (default: `address`) |
| `--timeout` | POV timeout in seconds | No (default: 120) |
| `--build-timeout` | Build timeout in seconds | No (default: 1200) |
| `--test-timeout` | Unit test timeout in seconds | No (default: 1800) |
| `--build-workers` | Worker hint for build orchestration | No (default: 4) |
| `--verify-workers` | Worker hint for verify orchestration | No (default: 4) |
| `--no-variants` | Disable POV variant verification | No |
| `--force-rebuild` | Force rebuild even if cached | No |
| `--inc-build` | Enable incremental builds (full build is default) | No |
| `--output` | Output file path | No |
| `--format` | Output format (`json`, `yaml`, `text`) | No (default: `text`) |
| `--verbose`, `-v` | Enable verbose logging | No |

`--patch` or `--patch-dir` is required. `--pov` or `--pov-dir` is required.

## Implementation

### Key Classes

- **`PatchVerificationEngine`**: Main orchestrator for patch verification
- **`PatchInfo`**: Data class for patch information
- **`PatchVerificationResult`**: Result of patch verification
- **`PatchVerificationStatus`**: Enum for verification status
- **`CpvStats`**: Per-CPV verification statistics
- **`VerificationScores`**: Aggregate scoring metrics

### Key Methods

```python
class PatchVerificationEngine:
    def verify_patch(
        self,
        benchmark_path: Path,
        patch: PatchInfo,
        harness: str,
        pov_path: Path,
    ) -> PatchVerificationResult:
        """Verify a single patch."""

    def verify_patches(
        self,
        benchmark_path: Path,
        patch_dir: Path,
        harness: str,
        pov_dir: Path,
    ) -> list[PatchVerificationResult]:
        """Verify multiple patches from a directory."""

    def verify_benchmark(
        self,
        benchmark_path: Path,
        harness: Optional[str] = None,
    ) -> PatchBenchmarkOutput:
        """Auto-discover and verify all patches in benchmark."""
```

### Execution Model

Patch verification executes sequentially in the current engine implementation.

`build_workers` and `verify_workers` are accepted for orchestration compatibility,
and may be used by higher-level distributed scheduling.

**Pre-caching** before verification:
- Repository is cloned once and cached
- Inc-build image is pulled once and cached
- Reduces repeated setup work across patches

### Timing Metrics

Per-patch timing:
- `build_time`: Time to compile patched code
- `pov_test_time`: Time running POV tests
- `unit_test_time`: Time running unit tests
- `elapsed_seconds`: Total time for this patch

Aggregate timing:
- `wall_clock_time`: Actual elapsed time for entire run
