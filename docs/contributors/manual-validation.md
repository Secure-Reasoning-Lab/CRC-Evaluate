# Manual Validation Guidelines

## 1. Ground-Truth Patch

- Patches are continuously verified through automated validation.
- All current patches are verified to correctly fix the target vulnerability.
- Each patch passes the current version of `test.sh`.
- If the ground-truth patch comes from the actual developer’s commit, we can trust it.

Important limitation  
- The unit tests used by `test.sh` have limited test coverage.
- As a result, automated validation may miss certain issues.
- Manual validation is required to identify gaps not covered by tests.

---

## 2. vuln.yaml

!!! IMPORTANT !!!
- Never blindly trust `vuln_analysis.md` or `vuln.yaml` generated by an LLM agent.
- All agent-generated outputs must be questioned and manually verified.
- The agent analyzes vulnerabilities with reference to the ground-truth patch.
	- If the ground-truth patch itself is incorrect, the vulnerability analysis should be treated as highly suspicious.

---

## Required Fields (Follow the RFC)

Add fields according to the RFC defined here:  
https://docs.google.com/document/d/1zweFtQT-EhAnimtMfr7XqTQN4LTvtKnUE7QlyImVF1c/edit?tab=t.0#heading=h.b9y1q86ktx4g

### Field Guidelines

- **id, name**
  - Leave them as-is.
  - They may be revised later in a batch if needed.

- **author**
  - Leave empty for now.
  - The author name will be filled in later based on commit history.

- **validator**
  - Add your name.

- **description**
  - Provide a clear vulnerability description of reasonable length.
  - No strict format is required.

- **difficulty_level**
  - Leave empty.
  - Will be assigned later based on CRS evaluation results.

- **cwes**
  - Multiple CWE entries are allowed.
  - Include all relevant CWEs.

- **origin**
  - `1-day`: the vulnerability is ported from a real-world vulnerability.
  - `synthetic`: the vulnerability was artificially introduced by the benchmark author.

  Tips  
  - When identifying a 1-day vulnerability, searching for the ground-truth patch is often the most efficient approach.
  - Benchmark authors are highly likely to have used the original developer patch.
  - For delta mode benchmarks, inspect the diff from base to ref.

- **release_date**
  - If `origin = 1-day`: use the official vulnerability disclosure date.
  - If `origin = synthetic`: use the CRSBench release date.
    - For now, set this to 02/01/2026 (subject to change).

- **reference**
  - Include all relevant links, such as:
    - Official patch diff
    - CVE page
    - osv.dev entry
    - Any other authoritative vulnerability references

---

## Locations

- **root_cause**
  - Identifying the true root cause is often difficult even for human reviewers.
  - If uncertain, omit `root_cause` entirely.

- **crash_site**
  - Must point to repository-internal code only.
  - Exclude:
    - libFuzzer-related functions
    - Sanitizer runtime functions
    - Standard library code

Strict rules  
- `root_cause` and `crash_site` must never reference harness code.
